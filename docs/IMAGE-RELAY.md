# BPS 自动发送图片（0.5.23）

0.6.6 修复（2026-09-27）：PDF/Word 渲染返回的 detail=original 已兼容映射为 high，图片字节不变；下文 0.5.23 的 original 拒绝策略仅为历史行为。文件附件支持和本次验证见 [PDF / Word 输入说明](DOCUMENT-INPUT.md)。

直接发送图片或截图即可。0.5.23 按官方前端区分用户消息图片与工具结果截图，不需要图片开关、域名、端口、目录或反向代理配置。配置页提供模型与账号选择，并显示图片支持说明。

本文文件名保留为 IMAGE-RELAY.md，方便已有文档链接继续使用；0.5.16 引入原生附件上传，0.5.23 修正工具截图的发送路径。0.5.14 / 0.5.15 的自托管中转记录只作为历史资料保留。

## 发送流程

1. 客户端照常把图片作为 input_image 发到 Sub2API。消息 content 和 function_call_output / custom_tool_call_output 的 output 数组中的截图均支持。
2. 插件完整校验本请求所有内嵌图片，包括工具截图；验证 Base64 全部字节、声明 MIME、文件格式、尺寸和资源预算。仅用户消息中的 Base64 图片使用宿主本次调度账号的认证信息和代理，通过 multipart/form-data 的 file 字段上传原始图片。默认端点为 https://bps.openai.com/basispoints/api/attachments，与 Responses 端点同源、同目录。
3. 取得返回的 openai_file_id 后，仅将用户消息图片块中的 image_url 替换为 file_id。function/custom 工具结果中的截图保留原始 data URL 的 image_url，不上传附件、不改成 file_id。
4. 两条路径均支持 detail=auto/low/high，缺失或 null 时补为 auto；显式 low/high 保留。再把完整对话交给 BPS 中已勾选的本次请求模型（六种支持模型之一）。

模型、账号与代理均沿用原请求。普通文字、工具参数、相邻内容顺序和 JSON 大整数不按图片重写。已有 HTTPS 图片地址和有效 file_id 可直接使用。未命中插件账号或模型范围的请求仍原样透传。

上传前完成所有内嵌图片校验；上传失败时不发送后续 Responses 请求。只有全部上传成功后才修改图片引用。如果多图上传中途失败，前面已上传的文件可能仍留在提供方；本插件不虚构删除接口或承诺上游文件清理。

## 安装与使用

安装并重新加载 0.5.23，确认配置页运行版本后即可在客户端发送图片。模型选择、账号白名单和宿主灰度共同决定哪些请求由插件接管。默认勾选 gpt-6-astra 和 gpt-5.6-sol；清空模型选择表示全部透传，清空账号选择仍表示不限制账号。

用户消息图片通过原生附件上传，工具截图保留 data URL；无需图片开关、图床或反向代理配置。

本次针对“发送图片后，已开始修改或调用工具再出现 422”的反馈修正协议差异。通用 422 截图不能证明实际服务器拒绝的唯一原因，若升级后仍失败，应结合请求 ID 和脱敏诊断进一步定位。

## 输入与资源边界

| 项目 | 0.5.23 的边界 |
| --- | --- |
| 图片格式 | PNG / JPEG / GIF / WebP，完整校验 Base64、声明 MIME、文件格式和尺寸 |
| 单张解码大小 | 最多 20 MiB |
| 请求内嵌图片出现次数 | 最多 20 次；用户图片和工具截图共同计数，重复图片每次出现仍计数 |
| 请求解码后图片总量 | 最多 32 MiB；包括工具截图，重复图片每次出现仍计入 |
| 单张像素 | 最多 64 × 1024 × 1024 像素 |
| detail | 支持 auto / low / high；缺失或 null 补 auto；original 明确拒绝，不静默降级 |
| 引用方式 | 支持内嵌 Base64、有效 file_id、已有 HTTPS URL；不支持非 HTTPS 外部 URL |
| 内嵌图片请求 JSON | 图片工作准入上限 64 MiB |
| 图片请求并发和估算预算 | 包含只带工具截图的请求；最多 32 个准入请求，合计 512 MiB 估算预算 |
| 附件上传并发 | 每进程最多 32 个活动上传，仅用户消息图片需要上传 |
| 上传响应 | 最多读取 64 KiB，必须包含有效 openai_file_id |
| 附件缓存 | 最多 512 项，仅存文件 ID 等元数据，最长 30 分钟 |

图片请求准入在原请求体读取和 JSON 解析完成、识别出有类型标记的内嵌图片之后执行，随后才进入上传与协议转换。估算预算按实际 JSON 长度的 8 倍预留，最小计入长度为 1 MiB。它限制准入的图片工作，不限制初始读体或 JSON 缓冲，也不是进程 RSS 的硬上限。超大图片请求返回 413；预算不足返回 503 与 Retry-After: 1。纯文本及不接管请求继续按原有规则处理。

## 原图与重复图片

插件不压缩、不缩放图片，也不修改客户端指定的可支持精度。用户消息的 Multipart 将 Base64 图片逐段解码后直接写入当前账号的 HTTP 传输，避免生成额外的完整解码图片副本或落盘文件；原始 JSON 请求体仍按正常请求流程读取和解析。工具截图保持原始 data URL，不调用附件接口，也不能绕过完整图片校验。

同请求的相同用户消息图片只上传一次。跨请求复用由完整图片内容和 MIME 的带密钥摘要、可信会话作用域、账号、认证令牌以及附件端点共同隔离。缓存仅保留文件 ID、摘要和时间等有界元数据，不缓存图片字节；缓存期限从上传开始最多 30 分钟，不因读取续期。工具截图不产生新的附件 ID 缓存。

可信会话由宿主隔离后的 conversation_id 提供。没有可信标识时使用请求独立作用域，不跨请求复用；客户端自行提供的普通会话别名不能代替这个边界。相同作用域的并发上传可共享结果，等待者可独立取消。

30 分钟仅代表插件本地复用期限，不代表 BPS 文件的有效期、提供方的保留期限或删除时间。插件重启后缓存消失，客户端再次提交用户消息图片时会自动重新上传。

0.5.15 的 [性能报告](PERFORMANCE-0.5.15.md) 测量的是旧自托管路径中的本地处理与写盘，不包含本版原生上传。不能将其中的百分比当作当前版本的端到端加速结论；本版没有发布真实 BPS 上传或识图速度的测量结果。

## 错误与排查

- 400 invalid_image / unsupported_capability：按 path=input[n].content[m] 或 output[m] 检查图片数据、大小、引用和 detail。错误不回显 Base64、真实文件 ID 或图片内容。
- 401 / 403 attachment_upload_error：当前账号的用户消息图片附件请求被上游拒绝，检查该账号授权和访问权限。工具截图本身不触发附件上传。
- 工具执行后出现 422：确认已重载 0.5.23，检查工具截图是否仍为 image_url data URL，以及缺失/null detail 是否补为 auto。422 也可能来自其他请求字段，需结合请求 ID 与脱敏诊断确认，不能仅凭状态码认定账号或配置损坏。
- PLUGIN_RATE_LIMITED：BPS Responses 或附件接口返回 HTTP 429，稍后重试。0.5.22 起通过插件错误帧隔离，避免误暂停宿主 Codex 账号；当前官方宿主通常返回 502 或流式失败，原始 429 可在宿主诊断查看。
- 502 invalid_attachment_response / attachment_transport：附件接口返回无效文件 ID、异常响应，或当前账号的代理/网络请求失败。
- 413 request_too_large / 503 image_request_busy / attachment_busy：减小图片请求或稍后重试。

附件上传不跟随重定向，避免凭据随重定向发送。错误路径保留适用的 HTTP 状态码，并使用固定安全提示；上游错误中回显的原生文件 ID 和旧图片链接令牌会脱敏。排查这些问题不需要配置图片公网入口。
