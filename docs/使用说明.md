## 一、这个插件做什么

适用于 Sub2API 官方版的插件，通过 OpenAI Excel（Basis Points）官方入口使用账号可用的官方模型。

只把**命中插件灰度且符合账号选择规则的 OpenAI OAuth 账号**中，**在配置页勾选的模型**的请求转发到 Basis Points 端点：

```
https://bps.openai.com/basispoints/api/responses
```

可选模型为 `gpt-6-astra`、`gpt-6-sol`、`gpt-6-luna`、`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`，默认只勾选 `gpt-6-astra` 和 `gpt-5.6-sol`。模型名去除首尾空白后精确匹配。

客户端（Codex / Responses 客户端）照常请求 Sub2API，符合上述条件时，本插件带上该账号的 access token，保留本次请求的模型名直打 Basis Points，再把结果还原成客户端能读的形式返回。未勾选的模型及其他模型（包括旧 `-excel` 别名、未知模型和宿主连通性测试使用的 `gpt-5.4`）均原样透传到宿主原本指定的上游。0.5.22 已移除固定算术 challenge 的特殊扫描与绕行：渠道监控也遵循模型和账号选择，命中 BPS 的请求会使用 BPS 额度；其 429 通过插件错误帧隔离，不写入 Codex 账号限流。

账号调度、Token 刷新、用量统计、计费仍然由 Sub2API 负责，插件不碰这些。

当前源码中，配置页的“一键检测原生 Codex”和逐账号“降智检测”通过现有接口准备、确认后台任务，固定请求原生 Codex，已经走 BPS 的账号也检测原生。任务拥有独立编号；单号固定所选账号，批量固定点击时的目录快照；正式路由设置不被待保存表单替换。默认仅支持单实例，忙碌时等待原任务结束。若显示“结果未确认”，可能已经提交，点击“继续查询上次检测”查询原任务；不要据此认定没有发出请求。普通“测试配置”仍只检查 TCP/TLS 连通性，不能判断账号 BPS 权限。详见 [任务协议](PLUGIN-DIAGNOSTIC-TASKS.md)。

### 图片发送

直接发送图片或工具截图即可，无需启用图片开关或填写其他设置。0.5.23 区分两条路径：用户消息中的内嵌 Base64 图片使用宿主本次调度账号及其代理上传 BPS 原生 attachments 接口，并以返回的 file_id 发送；function/custom 工具结果中的截图保留原始 data URL，不上传附件。仍使用原模型和原账号，不生成公网下载链接、不启动图片监听，也不在本地保存图片文件。

支持 PNG/JPEG/GIF/WebP、消息内图片和 function/custom 工具结果中的截图。原图不压缩；已有 HTTPS 图片和有效 file_id 保留，detail 支持 auto/low/high，缺失或 null 补为 auto，保留 low/high。0.6.6 将 original 映射为 high，图片字节不变。0.6.7 将每请求内嵌图片计数上限从 20 放宽至 128；单张仍最多 20 MiB、解码后共 32 MiB，单张最多 64 Mi 像素。消息图片、历史工具截图及重复图片共同计数，插件不删除或压缩历史。128 是插件资源保护边界，不保证上游支持所有请求；无效或超限图片返回带字段位置的明确 400。

0.6.6 同时支持 PDF/DOC/DOCX 的 input_file 原生附件上传。文件输入、限制、Word 工具执行和验证边界见 [PDF / Word 输入说明](DOCUMENT-INPUT.md)。

重复的用户消息图片上传自动去重，可信会话内仅缓存附件 ID 等元数据，最长 30 分钟；这不是上游文件保留期限。限制、错误排查与验证范围见 [自动发送图片说明](IMAGE-RELAY.md)。

## 二、安装

### 1. 生成签名密钥并打包

生产环境默认拒绝未签名包，所以必须签名：

```bash
go run ./tools/keygen -out ../basispoints-private/publisher
bash ./build.sh -signing-key ../basispoints-private/publisher.private -key-id my-publisher-v1
```

Windows 用 `.\build.ps1 -SigningKey ..\basispoints-private\publisher.private -KeyId my-publisher-v1`。

产物在 `dist/local.oai-basispoints-0.6.9.s2plugin`。

> 密钥保存在仓库外；已有发布密钥请复用，不要重复执行生成命令覆盖。`publisher.private` 只留在受控机器上，**不要**提交到仓库或复制到服务器。

打包后显式使用配套公钥验签：

~~~powershell
python -X utf8 tools/verify_package.py dist/local.oai-basispoints-0.6.9.s2plugin --public-key ../basispoints-private/publisher.public
~~~

### 2. 配置宿主信任这个发布者

在 Sub2API 的配置里加入公钥（`key_id` 必须和打包时用的一模一样）：

```yaml
plugins:
  allow_unsigned: false
  trusted_publishers:
    my-publisher-v1: "go run ./tools/keygen 输出的 public key"
```

本地调试图省事可以临时设 `allow_unsigned: true`，测完记得改回来。

### 3. 上传并启用

在 **插件管理页** 上传并安装 0.6.9 的 `.s2plugin`，打开配置页选择模型和账号，保存确认后启用。

**0.6.7 安装**：先停用并卸载旧插件，再上传新版签名包。卸载会删除旧插件配置，本版不兼容或迁移旧配置；安装后重新设置模型、账号、403 开关、绑定与灰度比例，再启用。原发布公钥无需更换，详细步骤见 [0.6.7 发行记录](release-0.6.7-2026-09-27.md)。

启用后还需在插件绑定里设置**灰度比例**：只有命中灰度的 OpenAI OAuth 账号才会走本插件，未命中的账号继续走 Sub2API 原来的路径。第一次建议先小比例灰度。

## 三、配置模型与账号

打开插件的配置页，勾选**要走 Basis Points 的模型与账号**，然后点保存。默认勾选 `gpt-6-astra` 和 `gpt-5.6-sol`，其余四个模型可按需开启。模型按版本分两排：上排为 GPT-6（Astra、Sol、Luna），下排为 GPT-5.6（Sol、Terra、Luna）。

账号列表显示完整账号名称，次级完整 ID 区分同名账号；空白名称回退 ID。改名会更新列表与已有检测摘要，保存始终按完整数字 ID 对应。逐账号“降智检测”只显示对应账号结果，不改选择。当前源码中，未开启自动模式时，“一键检测原生 Codex”仅在完整结果可信时勾选疑似降智账号、取消符合规则账号，失败、跳过及列表外账号保留原选择，必须点击保存才改变路由；自动模式下批量也只显示结果。任务编号和状态显示在结果区域；结果未确认时保留原选择。检测仍使用固定“17”回答规则，不代表可靠智力测评。

### 请求时区跟随出口 IP（0.6.7）

在“请求环境”区域打开“请求时区跟随出口 IP”，然后保存。开关默认关闭，独立于自动降智检测，可单独启用或关闭。为兼容现有配置，沿用旧字段名 `native_timezone_by_ip`（默认 `false`），现在共同控制原生 Codex 业务、BPS 业务和原生降智检测。通过实际转发账号的同一代理客户端向 ipapi.co 查询出口时区，查询成功缓存 6 小时，失败缓存 5 分钟。

该功能调整上述请求的环境上下文时区和相应日期。BPS 在协议准备前调整，后续重试和工具修复沿用同一时区；自定义 `responses_url` 同样生效。文件和图片上传本身不注入时间上下文，非 Codex 透传也不处理。关闭时不发起 IP 查询；查询失败保留原请求，不保证改善降智。实现边界见[请求时区说明](NATIVE-IP-TIMEZONE.md)。

### 原生 Codex 自动检测与切换（0.6.7）

在“原生 Codex 降智检测”区域打开“自动检测与切换”，检查“常规检测间隔（分钟）”，再点击保存。自动开关默认关闭，间隔默认 30 分钟、可选整数 5–1440；原生检测固定使用 gpt-6-astra，无需配置，独立于正常业务的 BPS 模型选择，旧模型配置不会覆盖固定值。关闭页面后后台仍继续运行。

首次或新账号检测分散在约 5–30 秒后开始；待确认的疑似降智或恢复在约 5 分钟后复测。连续两次有效结果一致才切换：原生疑似降智启用 BPS，原生恢复取消 BPS；失败、跳过、未检测及尚未确认的账号保留原选择或最后有效路由。常规间隔不改变固定的 5 分钟复测规则。

自动模式下手动勾选和全选锁定，账号列表显示后台实际有效路由、结果、复测进度及下一次计划时间。每批最多 8 个账号；0.6.9 起每账号使用配置超时（默认 300 秒），自动单批另留 5 秒余量，大目录按到期时间公平分批。手动批量按目标批次数计算总预算，请求预算最多 30 分钟，另留 5 秒余量。自动与手动检测不重叠，已有任务时需等待。

关闭自动并保存会停止后续调度、取消在途自动探针，保留最后一次有效路由；之后可以手动重新选择账号并保存。路由和调度状态保存在插件 KV，重启后恢复；这不代表旧手动任务会自动重跑。未完成或失败的检测不会当作降智处理。配置字段与故障边界见 [原生自动检测说明](AUTO-NATIVE-DEGRADATION.md)。

**403 自动停用开关**：bps_auto_disable_on_403 默认开启。开启时明确 BPS 403 会停用当前账号的 BPS，使用宿主 KV 持久保存；其他账号及宿主账号状态不变。关闭只阻止新停用，已有记录需明确重新勾选该账号并保存恢复。KV 写入失败会重试并显示错误，持久性仍依赖宿主 KV 可用。

BPS 403 保护优先于自动启用决定，但不阻止该账号的原生检测。原生检测返回 403 只记为检测失败，不创建 BPS 封禁。自动检测不会解除已有 BPS 封禁；需要恢复时，先关闭自动并保存，再重新勾选账号并保存。

### 基础账号选择规则

以下规则用于没有有效自动路由决定的账号。存在自动决定时以后台有效路由为准，BPS 403 保护、模型选择和宿主灰度仍然有效；关闭自动后保留的有效决定需通过手动重新选择并保存来替换。

0.5.24 的新模式使用 `auto_select_new_accounts=true`：未列入 `excluded_account_ids` 的账号默认允许使用 BPS。后台直接根据排除表判断，之后新增账号即使尚未打开配置页、已保存的 `account_ids` 快照尚无该 ID，也能对已选模型使用 BPS。宿主必须先调度该账号、命中插件灰度并将请求交给插件；本功能不改变宿主调度或灰度。

界面读到新增账号时自动勾选。手动取消并保存后，账号加入持久排除表；刷新、重开页面或再添加账号不会把它勾回来。也可以点击“全选列表账号”一次勾选当前列表中的全部账号并移除它们的排除记录，再点击保存。暂未出现在列表里的已保存选择与排除记录保留；加载、保存和回读确认期间不可全选，列表为空时按钮禁用，已全选时显示“已全选列表账号”并保持可点击。重复账号只显示一次，无有效账号时显示空列表提示；保存失败会保留当前选择，可重新保存。

**旧配置需要区分迁移前后**：非空旧白名单先按原规则运行。打开配置页，成功读取完整账号目录、确认选择并保存一次后，将当时未勾选的账号迁入排除表并启用新模式，尊重旧的取消选择。旧空白名单原本不限账号，因此页面显示为全选。不要把旧版“空账号列表不限账号”理解为新版界面的“取消全部账号”。

| 选项 | 含义 |
| --- | --- |
| 不勾选任何模型 | **全部透传**到宿主上游，不转发到 Basis Points |
| 勾选若干模型 | 只有这些模型在同时满足账号选择规则和插件灰度时走 Basis Points；未选模型原样透传 |
| 新模式下不勾选任何账号并保存 | 当前全部已知账号加入排除表；未来新增账号仍默认接入。若要停止全部 BPS 请求，请取消全部模型并保存 |
| 新模式下新增账号 | 默认接入，不要求 UI 已打开，也不要求 `account_ids` 快照已包含该 ID |
| 未迁移的旧配置中账号白名单为空 | 保留原来的**不做账号限制**行为；页面显示为全选 |
| 新模式下取消某个账号并保存 | 该账号持久排除；其请求由插件**原样透传**到宿主的上游 |
| 未迁移的旧配置中账号白名单非空 | 暂按原白名单处理；成功读取账号目录并保存后，原未勾选账号迁入排除表 |

**凭据与代理始终来自宿主本次调度的那个账号**，插件不做账号替换、不做轮询：

| 宿主是否给出站令牌 | 插件行为 |
| --- | --- |
| 给了 `Authorization` | 直接用；代理用宿主为该账号选定的代理 |
| 没给 | 按**同一个账号**解析身份，用它的令牌和它自己的代理 |

所以宿主的并发计数、限流窗口、用量归属都保持准确，也不会出现"用 A 的令牌从 B 的代理出去"。宿主透传的账号头保持权威（影子账号会刻意透传母账号 ID）。

⚠️ 宿主反向服务不可用（拿不到出站身份）时，插件按**不可重放**上报：换账号也解决不了，宿主的换账号重试对它无效 —— 不会再演变成"号池被挨个试穿、客户端只拿到一条与真实原因无关的 `503 Service temporarily unavailable`"。

除此之外**什么都不用填**——端点、超时、鉴权模式由插件内置默认值处理：

| 项 | 默认值 |
| --- | --- |
| Responses 端点 | `https://bps.openai.com/basispoints/api/responses` |
| 鉴权模式 | `chatgpt` |
| 超时 | 300 秒 |
| 默认勾选模型 | `gpt-6-astra`、`gpt-5.6-sol` |
| Basis Points 上游模型 | 保留本次请求的模型名 |
| 自动检测与切换 | 关闭，保存后生效 |
| 请求时区跟随出口 IP | 关闭，保存后生效；原生、BPS 和原生检测共用开关；成功缓存 6 小时，失败缓存 5 分钟 |
| 自动常规检测间隔 | 30 分钟，可设 5–1440 分钟 |
| 原生检测模型 | 固定 gpt-6-astra，无需配置，独立于 BPS 已选模型 |
| 原生检测端点 | https://chatgpt.com/backend-api/codex/responses，固定不受 BPS 端点配置影响 |

`enabled_models` 保存模型选择，默认启用 `gpt-6-astra` 和 `gpt-5.6-sol`，显式空数组 `[]` 表示全部透传。新模式由 `auto_select_new_accounts=true` 启用，`excluded_account_ids` 保存不走 BPS 的账号 ID；`account_ids` 是界面选择快照，不再是新账号接入的完整许可名单。后台在新模式下直接放行非排除 ID，所以不依赖配置页不断刷新和保存。

旧配置在迁移前仍使用 `account_ids` 的白名单语义：非空只允许列出的 ID，空列表不限账号。配置页读到完整账号目录后保存，会将旧未勾选账号迁入排除表并开启新模式。全新安装在配置页确认模型和账号并保存即可。

等待配置读取完成后再选择模型和账号。保存按钮会先提交，再重新读取并核对两种选择；出现“已保存，并已重新读取确认”后，关闭重开仍会显示勾选。读取失败时会暂时锁住保存，点击“重新读取”重试，避免用空选择覆盖原配置。

**历史版本记录**：`0.5.1` 修复保存按钮被宿主 iframe 的表单限制拦截的问题；`0.5.2` 修复流式首字缓冲；`0.5.3` 修复多会话工具目录和本地工具回放；`0.5.4` 修复协议级失败被当成传输错误上抛（现在会以 error 帧返回，宿主可正确归因且不会误换账号重放），并让模型直接调用的计划工具按客户端契约归一化。`0.5.6` 让流式失败不再丢原因：已输出内容后再遇到协议级失败时，改用协议内的 `response.failed` 事件收尾。`0.5.5` 把账号勾选改成**白名单**语义：勾选的账号走 Basis Points，未勾选的账号由插件原样透传到宿主的上游（等同于没启用插件），不会再出现"勾了账号反而把整个号池拖空、客户端只拿到一条与原因无关的 503"；白名单内账号解析不出凭据时按**不可重放**上报，错误里直接点名原因。`0.5.7` 修复子代理协作工具调用被当成密文（Codex 的 `collaboration.spawn_agent` / `send_message` / `followup_task`）：还原出的函数调用现在带显式空明文标记（`encrypted_function_args: []`），直接调用保留上游已有的非 null 加密元数据。

`0.5.8` 补齐上游提前 EOF、读取超时或其他读取错误、响应体超限时的流式收尾：已经输出内容后，以 `response.failed` 返回真实 `code`/`message`，丢弃尚未确认的工具调用，并补齐一个 `[DONE]` 和结束帧。经过校验的终止响应会立即完成，不再等待上游网络 EOF。上游网络问题本身没有被消除；发生真实故障时，客户端仍会得到明确的失败原因。

---

`0.5.9` 增加 15 秒空闲保活，覆盖尚无文本、工具等待校验、已经输出文本后继续思考等空窗。心跳与业务事件由同一发送者顺序写出；取消或下游发送失败时主动关闭上游读取。单次请求仍受 `timeout_seconds` 限制，心跳不会延长配置的总超时。工具还原兼容单一的 `args` / `arguments` / `input` 字段及可唯一解析的命名空间别名，仍保留参数 schema 校验和歧义拒绝。

`0.5.10` 加固并发配置更新、关停与连接池管理，并固定每个请求的认证模式快照。同会话多个请求乱序完成时，旧响应不会再覆盖新工具目录或恢复已经清空的工具。不同请求仍可并行；串行发送只限制同一条流。已通过直连/HTTP 代理各 64 路并发的本地混合成功、失败和取消回归，生产并发额度仍按宿主账号配置与上游实际限流执行。

同一会话并发发现多个工具时，目录合并也会原子完成；后续省略目录的请求仍能取得这些已发现工具，避免并发更新丢失造成 `unknown client tool`。

`0.5.11` 只转发精确的 `gpt-6-astra` 到 Basis Points，上游也使用 `gpt-6-astra`。其他模型均原样透传到宿主上游，旧 `-excel` 别名不再转换。旧模型配置字段在加载和保存时归一化，不能绕过这一限制；账号白名单保持原有语义。

`0.5.18` 新增精确模型名 `gpt-5.6-sol` 的 Basis Points 路由，与 `gpt-6-astra` 共用原有账号白名单规则，发送上游时保留各自模型名。模型名匹配前去除首尾空白；其他模型和旧别名仍原样透传。

`0.5.19` 增加六模型选择，默认勾选 `gpt-6-astra` 和 `gpt-5.6-sol`。安装后选择模型和账号并保存；清空模型并保存后全部透传，重新读取不会恢复默认勾选。

## 四、客户端怎么用

要使用 Basis Points，请先在配置页勾选需要的模型。请求模型名去除首尾空白后必须精确为以下任意一个：

```
gpt-6-astra
gpt-6-sol
gpt-6-luna
gpt-5.6-sol
gpt-5.6-terra
gpt-5.6-luna
```

模型已勾选、符合账号选择规则并命中插件灰度时，插件将请求转发到 Basis Points，发送上游时保留各自模型名。

| 客户端请求 | 实际走向 |
| --- | --- |
| 已勾选的六种模型之一 | 符合账号选择规则且命中宿主插件灰度时发给 Basis Points，保留请求模型名 |
| 未勾选的六种模型之一 | 原样透传到宿主上游，保留原模型名 |
| 旧 `gpt-5.6-sol-excel` / `gpt-5.6-luna-excel` / `gpt-5.6-terra-excel` 别名 | 原样透传到宿主上游，保留原模型名 |
| 其他任何名字（包括未知模型和 `gpt-5.4`） | 原样透传到宿主上游 |

`-excel` 后缀不触发转发或去后缀，只有配置页已勾选的精确模型名才能走 Basis Points。

思考等级支持 `low` / `medium` / `high` / `xhigh` / `ultra`。**上游没有 `max` 档位**，传 `max` 会自动降成 `xhigh`；不传就是 `medium`。

## 五、它到底改了什么（技术细节）

以下 BPS 转换只应用于宿主交给插件、已勾选模型且符合账号选择规则的请求；其他请求沿用宿主原本指定的上游。“请求时区跟随出口 IP”独立开关关闭时，未走 BPS 的请求按原 URL、方法、请求头、请求体和响应透传；开启后，其中符合原生 Codex 路径的请求会调整环境上下文时区及相应日期，非 Codex 透传不变。BPS 请求也受该开关控制，在以下协议转换前完成时间上下文调整。

1. **端点改写**：忽略宿主传进来的上游 URL，统一打到 Basis Points 的 Responses 端点。
2. **补齐请求头**：
   - `authorization: Bearer <access_token>`
   - `chatgpt-account-id` / `x-openai-account-id`
   - `x-basispoints-auth-mode: chatgpt`
   - 以及 Excel 客户端画像头（`x-openai-internal-basispoints-*`、`x-stainless-*`）
3. **账号 ID 来源**：优先用宿主透传的 `chatgpt-account-id`（影子账号会刻意透传母账号 ID）；头部缺失时才从 access token 的 JWT 里解析。
4. **请求体按 Excel 形状构造**：必须带 `model_selection: "explicit"`，否则上游会返回 422 `Invalid request body`（实测）。
5. **工具调用改写**：客户端的工具目录从上游请求里移除，改写成自然语言目录；上游返回的原生 `run_officejs` 传输调用会被还原成客户端真实的工具调用。模型偶尔会**绕过** `run_officejs` 直接调用目录里的工具，插件同样会还原；其中计划工具 `update_plan` 允许一次有界归一化（`step`/`description`/`title` 统一为 `step`，`done`/`todo`/`doing` 等状态统一为 `pending`/`in_progress`/`completed`），归一化结果仍要通过客户端声明的 JSON Schema。
6. **流式处理**：上游对 Responses 请求**总是回 SSE**（即使请求里写了 `stream: false`）。客户端要流式就合成 `response.*` 事件回放；不要流式就还原成 JSON 并改写 `Content-Type`。普通文本事件边到边转发，工具事件先暂存到终点再统一转换；转换失败时以 `ForwardResponseError` 帧结束本轮（`request_sent=true`），不留下半个可执行的工具调用。
7. **模型路由**：插件只将 `enabled_models` 中已勾选、去除首尾空白后精确匹配的六种支持模型转发到 Basis Points，上游保留各自模型名。未勾选模型、旧 `-excel` 别名、未知模型以及宿主连通性测试使用的 `gpt-5.4` 都**原样透传**回宿主的上游。不扫描提示词内容；渠道监控与普通用户请求遵循相同路由。
8. **账号代理**：真实转发沿用宿主传入的当前账号代理；需要解析身份时，也只使用当前账号解析出的令牌和代理。插件不替换或轮询账号，请求体和响应转换不会绕过代理。

---

0.5.23 自动处理内嵌图片：先按原始图片历史固定会话与回合标识，完整校验用户图片和工具截图，再仅为用户消息上传原生附件；工具截图保持 data URL。只处理有类型标记的图片内容，不把普通文字或工具参数中的任意内容当作图片。上传失败时不发送后续 Responses 请求；上游错误中的附件 ID 和旧图片链接令牌会脱敏。旧图片中转配置不再生效。

## 六、出问题时怎么排查

先查看配置页的保存提示和底部状态，以及宿主的插件诊断日志。常见现象：

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| **提示 unknown client tool absent from the active catalog** | 固定示例可能使用 exec_command，但本轮只声明 functions.exec 自定义执行器；描述内的嵌套 helper 不是独立中继目标 | 升级至 0.5.20 并重载（包含 0.5.15 的首轮修复）。插件按本轮目录生成格式指引；首次工具交互出现单个目录外调用且尚未发出工具时，最多纠正一次。原调用不执行，纠正后仍校验目录及参数；已有工具历史、多工具或再次无效仍会失败 |
| **发送图片后，已开始修改或调用工具再出现 422** | 旧版把工具截图也转换为用户附件 file_id，与官方工具结果形状不同；通用 422 还可能有其他请求校验原因 | 升级并重载 0.5.24，确认运行版本后重新发起请求；工具截图应保留 data URL，缺失/null detail 补为 auto。若仍失败，结合请求 ID 和脱敏诊断检查具体字段，不能仅凭截图断言唯一根因 |
| 图片返回 400 invalid_image / unsupported_capability | Base64、图片格式、大小、图片引用或 detail 不受支持 | 按安全字段位置检查图片；detail 使用 auto/low/high，图片无需额外配置 |
| 图片返回 attachment_upload_error / invalid_attachment_response | BPS 附件接口拒绝请求或没有返回有效文件 ID | 确认当前账号权限、令牌与代理；不要配置公网图片地址。查看安全错误码，真实识图仍需部署环境验证 |
| 新增账号未走 BPS | 旧非空白名单尚未迁移，账号已被排除，模型未勾选，或请求未命中宿主插件灰度 | 确认运行 0.5.24；旧配置打开配置页，成功读取目录并保存一次；检查排除表、模型选择及宿主灰度。新模式不要求再次打开页面才允许后来新账号 |
| 取消全部账号后，后来新账号仍走 BPS | 新模式只排除保存时已知的账号，后来新增账号仍默认接入 | 若要停止全部 BPS 请求，取消全部模型并保存，或在宿主停用插件 |
| 一键检测显示 upstream response could not be read | 旧版单账号 8 秒预算、等待 EOF 及泛化错误会掩盖读取失败原因；不凭该消息确定宿主具体账号的根因 | 升级并重载 0.5.24；新版区分超时、取消与截断，收到 SSE 完成事件后立即提取回答。单次失败不判为降智；仍失败时检查具体脱敏错误、代理和上游状态 |
| 原生检测显示 upstream returned HTTP 403 | 当前源码的 gpt-6-astra 探针被原生 Codex 拒绝；仅凭状态码无法确定账号权限、代理出口或上游策略的具体原因 | 检查账号凭据、模型权限及关联代理；只记为检测失败，不判为降智，不改变路由，也不会触发 BPS 403 封禁 |
| 自动检测只显示待复测，路由尚未切换 | 首次有效结果需要确认，或之前的错误中断了连续结果 | 等待约 5 分钟后的复测；连续两次一致才切换，失败或跳过保留最后有效路由 |
| 关闭自动检测后仍有账号走 BPS | 关闭会保留最后有效路由 | 关闭并保存后，手动重新选择账号并保存；若要停止所有 BPS 请求，可取消全部模型或在宿主停用插件 |
| 原生连续降智但 BPS 仍显示已禁用 | 已有 BPS 403 停用记录优先于自动启用结果 | 先关闭自动并保存，再明确重新勾选该账号并保存；自动结果不会解除封禁 |
| 图片返回 413 / 503 image_request_busy / attachment_busy | 图片请求超过大小或并发预算 | 减少图片或稍后重试，详见自动发送图片说明 |
| 配置页显示“读取配置失败” | 管理会话失效、bridge_token 缺失或宿主请求失败 | 从插件管理页重新打开配置，或点击“重新读取”；无需用默认值覆盖配置 |
| 点保存没有反应，重开后未勾选 | 旧版保存按钮被 iframe 的表单限制拦截 | 升级至 0.5.1 并重新打开配置页，保存后应显示已重新读取确认 |
| 流式回答首字明显慢 | 旧版等待整个 SSE 完成后才做工具转换 | 升级至 0.5.2；普通文本会先流出，工具调用仍会安全转换 |
| 多会话读不到本地文件或工具不执行 | 会话间工具缓存/目录隔离不完整，或后续请求省略工具目录 | 升级至 0.5.3；会话目录会继承，工具调用按会话隔离 |
| **客户端报 `stream disconnected before completion: ... error decoding response body`** | 流中途失败，或长时间静默触发代理空闲超时；旧版部分路径没有完整终止事件或保活 | 升级至 0.5.9；每 15 秒空闲发送注释心跳；已输出内容后的失败以 `response.failed` 给出 `code`/`message`，丢弃待确认工具并补齐 `[DONE]` 和结束帧；有效终止响应立即完成。真实网络断开、客户端取消和总超时仍需按原因排查 |
| **提示 `Basis Points returned an unknown, ambiguous, or invalid client tool call`** | 工具信封的参数字段别名、命名空间解析不兼容；也可能确实调用了目录外工具或提供了非法参数 | 升级至 0.5.9；支持可确定性还原的参数字段和名称别名。仍不合法的调用会返回不包含原始参数的具体原因，不能靠忽略 schema 或执行未知工具绕过 |
| **一启用插件，账号就显示限流/异常** | 旧版可能将宿主使用普通模型（默认 `gpt-5.4`）的账号连通性测试发到 Basis Points，被以 `403 basispoints_model_access_changed` 拒绝 | 升级至 0.5.20；插件仅转发配置页已勾选的支持模型，账号测试使用的 `gpt-5.4` 会原样透传到宿主上游 |
| **BPS 429 后账号被暂停** | 旧插件把 BPS 独立额度的 429 交给宿主 Codex 限流处理 | 升级并重载 0.5.22；BPS 429 改为 PLUGIN_RATE_LIMITED 插件错误，不暂停整账号。官方宿主通常向客户端返回 502/流式失败，详细原因为 HTTP 429。此前误记的限流需确认后清除或等其到期；真实 Codex 限流保留 |
| 整轮回答失败并提示 `invalid_tool_call` / `basispoints_protocol_error` | 上游这一轮的传输调用无法确定性还原（工具不在目录里、参数不符合 schema、并行调用中有一个非法） | 升级至 0.5.9；按具体失败原因检查工具目录、名称和参数。已开始的流通过 `response.failed` 结束，不会释放半个工具调用给客户端执行 |
| 计划工具（`update_plan`）调用被拒 | 模型直接调用计划工具，且状态/描述字段用了 `done`、`todo` 这类别名 | 升级至 0.5.4；归一化后仍不满足声明 schema 的调用会照旧拒绝 |
| 保存结果未确认 | 宿主回读失败或返回的选择不一致 | 保留当前选择，重试并检查宿主日志；二次验证请及时完成 |
| 请求返回 401 `token_revoked` | 该账号的 access token 已失效 | 在账号管理里重新授权/刷新该账号 |
| 请求返回 401 其它信息 | 凭据缺失或账号 ID 不对 | 检查账号是否为 OpenAI OAuth 类型 |
| 请求返回 422 `Invalid request body` | 上游请求校验失败，仅凭状态码无法确定具体字段 | 先确认运行版本为 0.5.24，结合请求 ID、发生阶段和脱敏诊断排查；图片工具后续轮次参见上面的专项说明。无需盲目清空模型或账号配置 |
| 请求返回 4xx 且提示模型不存在 | 请求的模型未被对应上游接受 | 确认模型名属于六种支持模型且已在配置页勾选，并检查账号权限；未选或其他模型走宿主上游，需检查该上游支持的模型 |
| 已选账号的请求立刻失败且未发出 | 宿主反向服务不可用 / 该账号解析不出 token | 检查宿主反向服务、该账号的授权与代理；插件始终跟随宿主当前调度账号，清空勾选不能修复凭据或服务故障 |
| 客户端收到一堆 `event:` 文本但它不是流式客户端 | 非流式客户端拿到了 SSE | 已在新版本处理；确认插件为 0.4.0 及以上 |

要看插件实际状态：配置页底部的状态行会显示 `插件版本 · 模型 · ready`。

## 七、安全须知

- 插件**只读取**宿主提供的 access token，不刷新、不落盘、不写进日志。
- 错误消息与诊断里会剥离 token、账号 ID、邮箱和图片内容。
- 插件拥有 Sub2API 服务用户同等的文件与网络权限，子进程不是操作系统沙箱，只应安装可信来源的签名包。
- `signature.json` 的 `key_id` 必须与 `trusted_publishers` 的配置键一致；轮换密钥时先发布带新公钥的宿主配置，再发新签名的包。
