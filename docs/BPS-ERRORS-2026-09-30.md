## 修复细节

- 封装兼容修复与拒绝边界见 RELAY-SERIALIZATION-2026-09-30.md。
- 错误继续使用原有 invalid_tool_call 消息与请求级分类；已开始的 SSE 增加
  error.reason：relay_outer_arguments、relay_code_envelope、relay_nested_envelope、
  relay_tool_identity。字段只允许固定枚举，不返回工具源码或参数。
- 既有 RPC 错误契约仅支持 code/message/request_sent，不能在保持宿主兼容性
  的同时给所有缓冲错误添加任意 JSON 元数据；此路径仍保留原有错误。
- 有效强制工具选择在 BPS 参数重写、上传和状态检查前走宿主原生上游。
  未声明、冲突或错误类型的工具选择仍被拒绝；auto/none 继续使用 BPS 中继。
- 限流优化只处理真实 BPS HTTP 429 的单一有效 Retry-After（秒或 HTTP 日期），
  支持等待上限 24 小时。缺失、冲突、过期、溢出或超出支持范围时不猜测等待。
  不等待、不重试、不切换账号/代理/原生路由。短期状态只在进程内，容量有界，
  按账号、模型、端点、代理及认证身份的摘要隔离，不存储明文凭据。
- 首次 429 保留原有错误；后续命中等待期的同范围 BPS 请求返回安全的剩余
  秒数。沿用不可跨账号重放的 RPC 标记，避免宿主把 BPS 限制套到原生 Codex。
- 附件上传传输失败仅增加固定的 error.reason：timeout、dns、tls、dial、
  connection_closed、generic。保留原状态码、错误消息及取消语义，且每次上传
  仍只尝试一次；不把底层错误文本、URL、证书内容或代理凭据写入响应。

## 实测

用户明确授权使用其新导出的一个 OAuth 账号及对应 SOCKS5 代理。
通过插件实际 Forward 路径测试 gpt-6-astra / low，共 3 次 HTTP 请求，全部 200：
函数中继、自定义中继、合成工具结果回传后的最终确认。没有执行实际客户端工具，
没有额外纠正请求或重试。多行、引号、CRLF、制表符、Windows 路径及首尾空白
逐字节一致；SSE 的完成事件、[DONE] 和 End 帧完整。

三阶段分别耗时 5.154、6.194、3.702 秒，测试始于 2026-09-30 19:03:17 北京时间。
这证明该账号/代理在测试时可用，不代表所有历史账号的认证、访问权或额度已经恢复。
导出文件保持原样，令牌和代理密码没有写入源码或测试日志。

## 证据限制

数据库只留已转换的失败终态，没有导致失败的原始工具 arguments。附件错误
也未保存底层网络阶段或上传大小；429 的等待字段全部为空，不能据此判断上游
原始响应是否包含 Retry-After。新增诊断用于后续精确定位，不能回填历史原因。

脱敏统计、样例和实测记录保存在忽略目录 build/relay-diagnostics。
本次未执行原始 SQL、未修改备份、未发布或替换线上插件。
